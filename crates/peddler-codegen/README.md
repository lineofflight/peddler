# peddler-codegen

`peddler-codegen` generates the API code of the [`peddler` crate](../peddler/README.md), and the Ruby methods that call it, from Amazon's Selling Partner API models.

It is a development tool. It is not published, and neither the gem nor the crate ships it: both build from the generated code that is committed.

Peddler has 2 generators. This one writes Rust, and the Ruby method of each operation with its documentation. The [Ruby generator](../../lib/generator/README.md) writes the typed Ruby models.

## What it reads

- `selling-partner-api-models/`, a checkout of [Amazon's models][models] at the revision in `selling-partner-api-models.sha`. It reads the 70 API models under `models/` that `src/manifest.rs` lists, and the 55 report, feed, notification and Data Kiosk schemas under `schemas/` that `supplemental-sources.json` lists.
- `pagination.json`, which says which operations return pages and how to ask for the next one.
- `lib/generator/patches/`, 4 JSON patches that repair notification schemas. The Ruby generator applies the same ones.

## What it writes

| Path | Holds |
| --- | --- |
| `crates/peddler/src/apis/<api>/models.rs` | the typed models of an API version |
| `crates/peddler/src/apis/<api>/facade.rs` | for each operation, a parameter struct, an async function and, where it pages, a `*_pages` function |
| `crates/peddler/src/apis/dispatch.rs` | `apis::execute`, which runs an operation by its key with JSON arguments. The Ruby extension calls it |
| `crates/peddler/src/apis/pagination.rs` | the pagination mapping of each paged operation |
| `crates/peddler/src/{reports,feeds,notifications,data_kiosk}/` | the typed models of the other schemas |
| `lib/peddler/native/apis.rb` | the class of each API with the Ruby method of each operation, the method of each API on `Peddler::Client`, the YARD comment above each of them, and the pagination mappings |
| `sig/peddler/native/apis.rbs` | the signatures of those classes and methods |
| `crates/peddler-codegen/operation-inventory.json` | every operation with its method, path, rate, parameters, responses and pagination |

Every Rust file starts with `// Generated by peddler-codegen. Do not edit.`, and the Ruby and RBS files carry the same line as a `#` comment.

## Running it

You need a stable Rust toolchain, Git, and Ruby with `bundle install` done. Ruby converts the Data Kiosk schemas, with the `graphql` gem.

From the repository root:

```sh
# Check out Amazon's models at the pin, then generate
bundle exec rake generate:rust

# The same, comparing with the files on disk and writing nothing
bundle exec rake generate:rust:verify
```

`bundle exec rake generate` runs this generator and then the Ruby one. `bundle exec rake generate:verify` regenerates everything at the pin and fails if a committed file changes. `bundle exec rake generate:update` moves the pin to Amazon's latest revision first.

The generator is a Cargo workspace of its own, with its own `Cargo.lock`, so every `cargo` command names its manifest:

```sh
bundle exec rake generate:rust:setup
cargo run --manifest-path crates/peddler-codegen/Cargo.toml --locked -- --root .
cargo run --manifest-path crates/peddler-codegen/Cargo.toml --locked -- --root . --check
cargo test --manifest-path crates/peddler-codegen/Cargo.toml --locked
```

The tests read the pinned checkout, so run the setup task first. `cargo test --workspace` at the repository root doesn't run them: the root workspace holds the crate and the extension only.

| Flag | Meaning |
| --- | --- |
| `--root <path>` | the repository to read from and write to. The default is the one the generator is in |
| `--output-root <path>` | write to, or compare with, another directory |
| `--check` | write nothing, and fail if a generated file is missing, differs or is no longer generated |

## What it guarantees

- It runs only on the pinned revision. The checkout must be at the pin, and the files it reads must be tracked there and unmodified.
- It reads exactly the files it lists. If Amazon adds or removes an API model or a schema, generation fails and names the file, until `src/manifest.rs` or `supplemental-sources.json` is updated. A new API is a deliberate edit.
- The same input gives the same bytes.
- It writes all or nothing. Every file is generated before any is replaced.
- It refuses what it has no rule for, and says where. A refusal names the spec file and the operation, such as `catalog-items-api-model/catalogItems_2022-04-01.json: searchCatalogItems: unsupported default for a body`.

## Operations

`src/clients.rs` reads each operation of a model: its method and path, its rate, its parameters and their types and defaults, the body, and the model of each successful response. `src/facades.rs` writes the Rust functions and the Ruby methods from that, and `src/docs.rs` the comments above the Ruby ones.

A generated function builds its request itself. It escapes each path parameter as 1 segment. It joins an array into 1 comma-separated query parameter, or repeats the parameter where the model says `collectionFormat: multi`. It serializes the body as JSON.

It doesn't check a value against the model's constraints, such as a pattern or a maximum: Amazon does. It keeps the defaults the model declares.

The rate is the requests per second in the usage plan table of an operation's description, the only place a model has it. The generator reads it as Peddler 5 did, and a generated function hands it to the client with its request. The client waits by it before it retries a 429. An operation without a usage plan, or with a rate of `n`, which varies by seller, has none. A usage plan the generator can't read a number from fails generation, so a change in how Amazon writes the table can't go unnoticed.

An operation with 1 successful response returns `TypedResponse<T>`. One with several returns a type with a decoder for each status, such as `json_200` and `json_202`. One without a model returns the raw `Response`.

A Ruby method takes the required parameters in order and the optional ones as keywords, under the names Peddler 5 used. It passes each argument through `Peddler::Native::Arguments`, which takes the forms Peddler 5 took and names the argument in what it raises.

Each Ruby method and API class has the YARD comment Peddler 5 gave it: the model's description, a note where the operation can run in the sandbox, each parameter and what it returns. A `*_pages` method and an API's method on the client have 1 line. A line break in a model's text can't end a comment and start code: none gets through the function that writes the comment lines.

To add an API version, add a `ModelSpec` to `src/manifest.rs` with the model's path, its module name, its family and version, and whether it is the latest of its family. `client.<family>` in Ruby is the latest.

## Models

[Typify](https://github.com/oxidecomputer/typify) writes the models from a model's definitions, after `src/models.rs` has normalized them:

- A number is a `serde_json::Number` with arbitrary precision, so no digit of an amount is lost.
- A string enum stays open: a value Amazon adds later still decodes.
- A default is removed, so that a field Amazon didn't send stays absent.

## Pagination

`pagination.json` is the only source of pagination. Nothing is inferred from names when a request runs.

A mapping names the `operation`, the `input` (a JSON pointer to the argument that carries the token) and the `output` (a JSON pointer to the next token in the response). 79 operations are mapped.

A `continuation` may also name another `operation` for the pages after the first.

By default, the request for a next page repeats every argument and replaces the token. A `continuation` changes that:

| Key | Effect on the next request |
| --- | --- |
| `keep` | send only these arguments and the token |
| `drop` | leave these arguments out |
| `set` | set these arguments to fixed values |
| `adapter` | go through an operation of its own, `<operation>.continue`, which sends only the token and the path parameters that are kept. `get_feeds` and `get_reports` need it |

`exclusions` lists 12 operations that look paged and aren't mapped, each with the reason.

Generation checks every mapping against the model. It fails if an operation takes or returns something that looks like a page token and is neither mapped nor excluded, so a new paged operation can't go unnoticed.
